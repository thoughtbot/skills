# Project Onboarding Skill

Deploys a team of specialized agents — each focused on a different lens — to explore a codebase and generate interconnected markdown documents with Mermaid diagrams. All agents run in parallel. Each owns one output file.

## Output

All files land in `.claude/onboarding/` at the project root:

| File | Agent | Contents |
|------|-------|----------|
| `index.md` | Coordinator (you) | Navigation hub, summary, reading order |
| `overview.md` | Scope Scout | Project purpose, tech stack, entry points, context diagram |
| `architecture.md` | Architecture Mapper | Module map, layers, boxes-and-arrows diagram |
| `structure.md` | Structure Guide | Annotated directory tree, naming conventions |
| `flows.md` | Flow Analyst | All data flows as sequence diagrams |
| `patterns.md` | Pattern Detective | Design patterns, conventions, code examples |
| `components.md` | UI Explorer | Component hierarchy, state machines (frontend only) |

## Step 1: Quick Scan

Before deploying agents, spend 60 seconds scanning the project root to determine:
- **Project type**: frontend / backend / fullstack / CLI / library
- **Language and framework**: check `package.json`, `Gemfile`, `pyproject.toml`, `go.mod`, etc.
- **Frontend presence**: does `src/components/`, `app/`, `pages/`, or similar frontend structure exist?
- **RSC usage**: grep for `'use client'` — if found, the project uses React Server Components and agents should document the server/client boundary
- **Existing onboarding**: does `.claude/onboarding/` already exist?

Use this context to build agent prompts and decide whether to include the UI Explorer.

## Step 2: Existing Onboarding Check

If `.claude/onboarding/index.md` already exists:
1. Read it to understand what was previously documented
2. Ask the user: "Onboarding docs already exist from a previous run. Do you want to: (a) full refresh — overwrite everything, (b) targeted update — pick specific agents to rerun, or (c) keep what's there?"
3. If updating, pass the existing doc content to agents as context so they can build on or revise it

## Step 3: Locate and Read Reference Files

This skill's agent playbooks live in `references/` alongside this SKILL.md. Find them with:

```
Glob: **/skills/onboard/references/*.md
```

Read each reference file you'll need before dispatching agents. You'll pass the contents of each reference file as that agent's prompt, combined with:
- The absolute project root path
- The absolute output file path (`.claude/onboarding/<file>.md`)
- The project context from Step 1 (language, framework, type, RSC usage)
- Any existing onboarding content (if doing a targeted update)

## Step 4: Deploy Agents in Parallel

**If `TeamCreate` is available:**

1. Create a team: `team_name: "onboarding", description: "Codebase onboarding run"`
2. Create a task per agent via TaskCreate
3. Spawn each agent via the Agent tool with `team_name: "onboarding"` and a `name` for each
4. Assign tasks to agents via TaskUpdate with `owner`
5. Wait for all agents to complete (they notify you via SendMessage when done)
6. Send `shutdown_request` to each teammate via SendMessage

**If `TeamCreate` is NOT available:**

Dispatch all agents in a **single response** using multiple Agent tool calls — one per role. All run concurrently. Wait for all to complete before proceeding to Step 5.

For both paths, include the frontend `ui-explorer` agent only if the project has frontend code (Step 1 finding).

## Step 5: Generate Index

After all agents complete, write `.claude/onboarding/index.md`:

```markdown
# [Project Name] — Onboarding Guide

> Generated by Claude Code on [date]. Run `/react-dev:onboard` to refresh.

## Quick Summary

[2-3 sentences describing what this project is, what it does, and who uses it.]

## Documents

| Document | What it covers |
|----------|----------------|
| [Overview](./overview.md) | Purpose, tech stack, entry points |
| [Architecture](./architecture.md) | System design, module relationships |
| [Structure](./structure.md) | Directory guide, naming conventions |
| [Flows](./flows.md) | All data flows as sequence diagrams |
| [Patterns](./patterns.md) | Design patterns and conventions |
| [Components](./components.md) | UI component hierarchy and state machines | ← only include this row if the project has frontend code

## Suggested Reading Order

1. **Overview** — understand what this is and why it exists
2. **Architecture** — see how the major pieces fit together
3. **Structure** — learn to navigate the filesystem
4. **Flows** — trace how data moves end-to-end
5. **Patterns** — learn the conventions so your code fits in
6. **Components** — (frontend) map the UI structure
```

## Step 6: Report

After all files are written, tell the user:
- Which files were generated and their paths
- Any notable findings (unusual patterns, surprising complexity, etc.)
- Suggested areas for a deeper dive

## Diagram Guidelines

Match diagram type to purpose — use Mermaid generously across all documents:

| Purpose | Mermaid Type |
|---------|-------------|
| System context / overview | `graph TD` |
| Module / layer relationships | `graph LR` |
| API calls, data flows | `sequenceDiagram` |
| Complex component state | `stateDiagram-v2` |
| Database schema | `erDiagram` |
| Decision / branching logic | `flowchart TD` |

Keep diagrams focused — 5-12 nodes. Split large systems into multiple focused diagrams.

---

## Quality Standards

Every document must be:
- **Didactic**: explain *why*, not just *what*. A new developer should understand the reasoning.
- **Navigable**: headers, tables, and cross-links to related onboarding docs.
- **Accurate**: document only what exists in the code. Do not speculate.
- **Concrete**: include real file paths, function names, and short illustrative code snippets.
